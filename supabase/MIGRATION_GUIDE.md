# Supabase 신규 테이블 생성 및 DDL 표준 가이드 (Atomic Unit Migration)

2026년 10월 30일부터 Supabase의 Data API(PostgREST)는 신규 테이블에 대한 자동 권한 부여 정책을 전면 중단했습니다.
또한 RLS(Row Level Security)가 비활성화된 테이블은 Supabase Security Advisor 경고(`rls_disabled_in_public`)를 유발하며 심각한 보안 취약점이 됩니다.

따라서 향후 데이터베이스에 새로운 테이블을 생성하거나 마이그레이션할 때는 반드시 아래 **4단계 원자적 단위(Atomic Unit)** 템플릿을 준수해야 합니다.

---

## 신규 테이블 표준 DDL 템플릿

```sql
-- ==============================================================================
-- 1단계: 테이블 정의 (CREATE TABLE)
-- ==============================================================================
CREATE TABLE IF NOT EXISTS public.<테이블명> (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ DEFAULT NOW() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    -- 비즈니스 컬럼 정의
    ...
);

-- ==============================================================================
-- 2단계: 명시적 권한 부여 (GRANT) - 10월 30일 Breaking Change 대응 필수
-- ==============================================================================
-- (1) 스키마 사용 권한 (기존 부여 상태이나 안전을 위해 선언)
GRANT USAGE ON SCHEMA public TO anon, authenticated, service_role;

-- (2) authenticated (로그인 사용자): 데이터 C.R.U.D 권한 부여
GRANT SELECT, INSERT, UPDATE, DELETE ON public.<테이블명> TO authenticated;

-- (3) service_role (백엔드 스크립트/퀀트 엔진/서버리스): 전체 관리 권한 부여
GRANT ALL ON public.<테이블명> TO service_role;

-- (4) 시퀀스 권한 부여 (BIGINT IDENTITY 또는 SERIAL 컬럼 존재 시 필수)
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO authenticated, service_role;

-- (5) anon (익명/비로그인): 외부 공개가 필수적인 정적/읽기 전용 데이터일 때만 SELECT 부여
-- GRANT SELECT ON public.<테이블명> TO anon;

-- ==============================================================================
-- 3단계: RLS 강제 활성화 (ENABLE ROW LEVEL SECURITY)
-- ==============================================================================
ALTER TABLE public.<테이블명> ENABLE ROW LEVEL SECURITY;

-- ==============================================================================
-- 4단계: 역할별 RLS 보안 정책 정의 (CREATE POLICY)
-- ==============================================================================
-- (1) service_role 정책 (무조건 ALL 허용)
CREATE POLICY "Allow service_role full access" ON public.<테이블명>
    FOR ALL TO service_role
    USING (true)
    WITH CHECK (true);

-- (2) authenticated 정책 (로그인 사용자 접근 제어)
-- [케이스 A: 전역/단일 사용자 자산 데이터인 경우]
CREATE POLICY "Allow authenticated full access" ON public.<테이블명>
    FOR ALL TO authenticated
    USING (true)
    WITH CHECK (true);

-- [케이스 B: 읽기 전용 매크로/통계 지표 데이터인 경우]
-- CREATE POLICY "Allow authenticated read access" ON public.<테이블명>
--     FOR SELECT TO authenticated

-- [케이스 C: 사용자별 데이터 격리가 필요한 경우 (user_id 컬럼 보유)]
-- CREATE POLICY "Allow individual user manage own data" ON public.<테이블명>
```

## 핵심 체크리스트 (Security Checklist)

1. [ ] **테이블 생성 후 RLS 활성화 확인**: `pg_tables`의 `rowsecurity` 값이 `true`인지 확인
2. [ ] **정책 존재 확인**: RLS만 켜두고 정책을 생성하지 않으면 `rls_enabled_no_policy` 경고 발생 (최소 1개 이상 정책 필요)
3. [ ] **Anon 권한 엄격 제한**: 외부 익명 클라이언트에 C.R.U.D 전체가 열리는 정책(`FOR ALL TO anon`) 절대 생성 금지
4. [ ] **시퀀스 권한 부여**: `BIGINT GENERATED ALWAYS AS IDENTITY` 또는 `SERIAL` 컬럼 사용 시 `authenticated`와 `service_role`에 시퀀스 `USAGE, SELECT` 누락 시 `INSERT` 시점에 권한 에러 발생
5. [ ] **백엔드 환경 변수**: 백엔드 적재 스크립트(`load_to_supabase.py` 등)는 반드시 `SUPABASE_SERVICE_ROLE_KEY`를 사용해야 함
